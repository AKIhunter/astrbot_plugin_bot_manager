# 向量用量恢复与对账逻辑

适用于 SDK 没有返回 Token、但共享向量网关仍保存可靠累计计量的场景。
当前使用标准库 SQLite，通过服务进程的独立线程每 15 秒执行
`service/server-embedding-usage.py`，写库身份为数据库所属用户 `astrbot`。
历史累计恢复本身不调用供应商 API。持续逐笔计量同时需要 LivingMemory
缓存核心及采集器的身份桥接补丁，2026-11-02 已上线。

## 数据结构

- 原 `usage_events` 保存可查询的汇总 Token 流水，`call_kind=embedding`，
  `plugin_id=unattributed`，不生成逐笔请求明细，`attempts=0`。
- 新 `usage_reconciliations` 按 `call_id` 保存来源、说明、覆盖区间、
  官方固定金额和恢复证据。
- `metadata.embedding_gateway_checkpoint_v1` 保存已审核登记的命名空间、
  模型、Provider、累计计数和上次观察时间。

首次恢复将“网关已计量累计”与“官方账单减去平台已知用量和网关累计后的差额”
分开入账。重复执行相同恢复 ID 返回已应用，不重复写入。
所有写入与检查点在一个事务中完成，失败回滚；数据库路径必须已存在。

## 计量与展示

旧累计模式的新增导入为当前累计减去上次检查点累计，缓存命中不产生新增上游 Token。
每个自然日一条网关增量汇总记录，后续追加到同一记录。
普通网关请求按文本输入价格计算，只有明确 Batch File 输入才使用其价格。
官方差额记录使用固定人民币金额，跳过免费额度重放。

报表日总、模型总量和 CSV 包含汇总记录；调用次数、延迟和小时分布不包含。
没有逐笔时间的记录显示日期和“汇总记录 · 非逐笔时间”，延迟显示 `--`。
原 SDK 未知请求保留原样，官方差额不能推断插件、请求数或精确小时。

## 逐笔流水与持续监控

LivingMemory 在供应商调用开始前持久化 `usage_journal`，响应后将真实 Token
和 `usage_totals` 在同一个事务中写入，再独立保存向量；缓存写失败不丢已付费用量。
`usage_journal_activation` 每个命名空间只冻结一次旧累计，此后不再导入旧总量增量。
新流水按 ID 重放，事务内更新同步检查点，跨日和重启不会重复入账。

采集器给网关传递可信的原 `call_id`、插件和模型身份，不传提示词或用户身份。
`usage_embedding_measurements` 保存报表投影，读取时覆盖原调用的计量字段，
避免采集器完成时覆盖补录。缓存命中和合并等待明确记为零新增消费；
调用取消后独立上游批次仍可按原身份回填。上游缺失计量保留未知。
无原调用身份的 HTTP 上游记录使用独立 `gateway:` ID，插件保持未归属。

后台仍每 15 秒执行同步，页面展示同步滞后、未知上游数、超时请求、
累计和流水是否一致。同步超过 90 秒／请求超过 120 秒提示异常；
服务日志保存异常，不发送群消息。官方历史差额金额保持固定。

## 停止条件与维护

未登记命名空间不执行导入。计数回退、时钟回退、未知上游用量、
跨自然日且累计存在未采集 Token、原 SDK 新增正 Token 时，旧累计模式暂停导入并报错。
新逐笔模式按记录时间持续导入，同时明确提示未知用量、异常及累计不一致。
管理员需检查 `journalctl -u bot-manager`，核实计数、覆盖区间和潜在重叠后
生成新的审核凭据；不得直接把全部累计重新加到账单。

本实现只登记当前确认的模型命名空间。改变网关模型或命名空间后需要重新核对。
官方快照截至时间不明确时，应单列“用户提供的账单基准”和“采集快照后的新增”，
不能将二者合计声称为重新获取的实时官方账单。

对应验证：`verification/test_embedding_reconciliation.py` 覆盖金额守恒、幂等、
事务回滚、重启、跨日、计数回退、SDK 重叠、原始流水保持与 CSV 审计字段。
